# Fashion Hub POS: Technical Documentation

## 1. System Overview

Fashion Hub POS is designed as a standalone Point of Sale system specifically tailored for premium retail clothing stores. It utilizes a monolithic repository containing two distinct Node.js projects: a Next.js (App Router) frontend and an Express backend. 

The primary goals of the system are:
- **Speed & Efficiency**: Allow a cashier to quickly scan a barcode or enter a SKU, adjust prices or quantities, and complete a sale within seconds.
- **Reliability**: Ensure inventory counts and financial reporting remain strictly accurate, even in the event of network timeouts, double-clicks, or server restarts.
- **Aesthetics & Branding**: Generate beautiful PDF invoices that can be immediately printed or sent via WhatsApp.

---

## 2. Core Architecture

### Frontend (Next.js)
- **Directory**: `/frontend`
- **Port**: `3000`
- **Responsibility**: Exclusively acts as the UI/Client layer. It fetches data and submits mutations to the backend. It uses **Tailwind CSS** for layout styling, employing mobile-first design principles (`grid-cols-1 md:grid-cols-2 lg:grid-cols-4`, `overflow-x-auto` for tables) to ensure cross-device responsiveness.
- **State Management**: Uses React state (`useState`, `useEffect`) and URL parameters (`useSearchParams`) to pass state seamlessly between pages (e.g. passing `editOrderId` from the Orders ledger to the Billing POS).

### Backend (Express)
- **Directory**: `/backend`
- **Port**: `5000`
- **Responsibility**: Handles all heavy lifting. The backend serves standard RESTful JSON APIs and implements robust business rules. 
- **Database**: Connects to MongoDB via Mongoose. Schema definitions are strict, using data types and nested sub-documents (e.g. `Order.items`, `Customer.stats`).

## 3. Data Integrity & Business Logic

### Idempotency Keys (Preventing Double Billing)
To guarantee exactly-once processing, the `completeSale` API expects an `idempotencyKey` (a unique UUID generated by the frontend). 
- If the cashier double-clicks the "Complete Sale" button, the backend intercepts the second request and returns the *same success response* as the first request, without deducting stock twice or duplicating the order.
- Idempotency records are cached in memory for 24 hours.

### Order Immutability & Reversals
Historically, Point of Sale systems lock orders to maintain financial auditing integrity. 
However, Fashion Hub supports an advanced **Reconciliation Engine**:
1. When a user edits a completed order, the frontend sends a `PUT /orders/:id`.
2. The backend opens a MongoDB Session/Transaction.
3. The items from the *original* order are mapped, and their exact quantities are re-added back to the inventory pool (`ProductVariant.stock`).
4. The customer's lifetime stats (`totalSpentPaisa`, `totalOrders`) are temporarily reduced.
5. The new cart is calculated. New stock limits are verified.
6. The new stock is deducted, new customer stats are derived (safely avoiding division by zero errors), and the Order document is overwritten.
7. An **Audit Log** and an **Inventory Movement** record of type `MANUAL_ADJUSTMENT` are created to ensure store owners know *who* edited the bill and *when*.

## 4. PDF Invoice Engine

Unlike many React apps that rely on messy HTML-to-PDF client-side libraries, Fashion Hub generates mathematically precise vector PDFs natively on the backend using **PDFKit**.

- **File Location**: `backend/src/services/invoice/InvoicePDFService.js`
- **Design**: The invoice features a dark/gold theme, drawing custom vector graphics (a hanger icon, a pentagon shield with a checkmark) entirely via PDFKit path commands (`bezierCurveTo`, `lineTo`).
- **Dynamic Configuration**: The PDF is built based on user preferences. For example, if the user turns off taxes via the settings page, the `InvoicePDFService` dynamically omits those calculation rows and merges subtotal/discount straight into the grand total.
- **Storage**: PDFs are saved persistently in `backend/storage/invoices/`. The frontend accesses them via the `/api/invoices/:id/pdf` route, which streams the raw PDF binary down to the browser.

## 5. Security & Authentication

- The application uses **Stateless JSON Web Tokens (JWT)**.
- Upon login (`POST /api/auth/login`), the backend validates credentials against the hardcoded/seeded admin hashes and returns a signed JWT.
- The JWT is stored in an `HttpOnly` cookie (`fashion_hub_session`).
- The backend's `authMiddleware.js` intercepts every protected API call, verifies the token's cryptographic signature, and attaches `req.user`.

## 6. Financial Formatting

All currency operations use **Paisa** (the smallest unit of INR, where ₹1 = 100 Paisa).
- **Why?**: Storing decimals in databases (e.g. `999.99`) often leads to floating-point rounding errors (`999.9900000000001`).
- All numbers are stored as Integers.
- The frontend divides by `100` right before rendering (using the `formatMoney` utility) and formats it natively to the Indian Rupee locale `en-IN`.
